# decision-analysis

이 Skill은 `.mason-report/events/`에 기록된 JSONL 로그(observed evidence)만을 근거로, Claude
Code가 하나의 사용자 요청을 어떻게 처리했는지를 재구성하는 절차를 정의한다.

## 핵심 원칙

- **이 Skill은 Claude의 비공개 chain-of-thought를 조회하지 않는다.** 로그에 없는 내용은
  아무리 그럴듯해도 "확인됨"으로 서술하지 않는다.
- 모든 서술은 다음 세 등급 중 하나로 명시한다.
  - `observed` (로그로 확인된 것): Hook 이벤트 또는 transcript에서 직접 확인된 사실
  - `inferred` (정황상 추정된 것): 관찰된 행동을 근거로 재구성한 설명
  - `unknown` (로그만으로 확인 불가): 현재 로그만으로 확인할 수 없는 내용
- "Claude가 이렇게 판단했다"라고 단정하지 말고, "관찰된 행동을 보면 이렇게 판단한 것으로
  추정된다"처럼 서술한다.
- **한국어로 리포트를 작성할 때는** 태그를 영어 단어 하나만 쓰지 않고, 위 괄호 안 한글
  표기를 함께 붙인다 — 예: `(observed, 로그로 확인된 것)`, `(inferred, 정황상 추정된 것)`,
  `(unknown, 로그만으로 확인 불가)`. 사용자가 다른 언어로 대화 중이라 리포트를 그 언어로
  작성하는 경우에는 이 한글 병기를 붙이지 않고, 해당 언어에 맞는 표기만 사용한다.
- **"실행 흐름" 불릿에서는 태그를 줄바꿈으로 분리한다.** 행동 설명 문장 뒤에 바로
  이어붙이면 한 줄이 길어져 가독성이 떨어지므로, 설명 문장을 먼저 쓰고 그 다음 줄에
  들여쓴 채로 태그(와 한글 표기)만 적는다:
  ```text
  - <행동 설명>
    (observed, 로그로 확인된 것)
  ```
  단, 트리거 매핑 **표** 셀 안에서는 이미 정해진 규칙대로 절대 줄을 바꾸지 않는다(표와
  불릿은 서로 다른 규칙을 따른다).
- 한 불릿 안에 등급이 다른 절(예: "A는 확인됐지만 B는 확인 불가")이 섞여 있으면, 태그
  하나에 두 등급을 몰아넣지 말고 하위 불릿으로 나눠 절마다 태그를 하나씩 붙인다
  (`examples/sample-report.md` 참고).
- transcript 파일은 비동기로 기록되어 현재 턴의 최신 메시지가 아직 반영되지 않았을 수
  있다. `Stop`/`SubagentStop` 이벤트의 `last_assistant_message`가 있으면 그것을 우선
  신뢰하고, transcript 재조회로 같은 `Stop` 처리를 반복 트리거하지 않는다.

## 분석 절차

1. **분석 대상 식별**: 분석할 `sessionId`와 (있다면) `promptId`를 확정한다. 단일 턴
   분석이면 가장 최근 `UserPromptSubmit`, 세션 분석이면 현재 `sessionId`의 전체 이벤트를
   기준으로 삼는다.
2. **최초 프롬프트 확인**: 해당 턴의 `UserPromptSubmit.data.prompt`를 확인한다. 이 값은
   저장 시 마스킹·길이 제한이 적용된 값이므로, 원문 그대로가 아닐 수 있다는 점을 인지한다.
3. **로드된 지침 확인**: 같은 턴(또는 세션 시작 시점)의 `InstructionsLoaded` 이벤트를
   모아 어떤 파일(`CLAUDE.md`, `.claude/rules/*.md` 등)이 로드됐는지 확인한다. 파일이
   "로드됨"과 그 내용이 "실제로 적용됨"은 별개다 — 이 구분은 8단계에서 다시 판단한다.
4. **시간순 정렬**: `PreToolUse`/`PostToolUse`/`PostToolUseFailure`/`SubagentStart`/
   `SubagentStop` 이벤트를 `timestamp` 기준으로 정렬한다. `promptId`로 명시적으로 연결된
   이벤트는 observed 근거로, `promptId`가 없어 시간 구간으로만 연결된 이벤트는 그 자체로
   inferred(약한 연결)로 표시한다.
5. **실제 수행된 행동 요약**: 정렬된 이벤트로부터 "무엇을 했는가"만 사실 그대로 요약한다
   (예: "Bash로 `npm test` 실행", "`src/foo.ts`를 Edit로 수정", "Explore 타입 Subagent를
   1회 실행"). 이 단계에서는 의도나 이유를 추측하지 않는다.
6. **관찰과 추정 분리**: 5단계 요약에 "왜 그렇게 했는가"에 대한 설명이 필요하면, 그 설명은
   반드시 `inferred`로 표시하고 근거가 된 관찰 사실을 함께 적는다.
7. **Skill 적용 여부 판단**: 아래 "Skill 활성화 등급"을 사용해 각 후보 Skill에 대해
   판정한다. 판정마다, 그 판단의 근거가 된 프롬프트 원문의 구체적 문구를 함께 표시한다
   (아래 "프롬프트 문구 → 트리거 매핑" 참고). 근거 문구를 특정할 수 없으면 "특정 문구 없음
   (unknown)"으로 남긴다 — 등급을 맞추기 위해 문구를 억지로 짜내지 않는다.
8. **Rule/지침 적용 여부 판단**: 3단계에서 확인한 지침 각각에 대해, 이후 관찰된 행동이
   그 지침의 내용과 일치하는지를 같은 4단계 등급 체계로 판단한다. 지침이 로드됐다는 사실만
   으로 "적용됨"이라 단정하지 않는다.
9. **최종 답변과 실제 행동 비교**: `Stop.data.lastAssistantMessage`(마스킹·길이 제한 적용됨)
   와 5단계 행동 요약을 비교해, 답변이 실제 수행 내용과 일치하는지, 누락되거나 과도하게
   단정된 부분이 있는지 확인한다.
10. **확인 불가 항목 표기**: 로그가 없거나, 파일이 회전(rotate)되어 유실됐거나, 이벤트
    스키마가 예상과 달라 판단할 수 없는 항목은 전부 `unknown`으로 남긴다. 빈 자리를
    그럴듯한 서술로 채우지 않는다.
11. **토큰 사용량 반영**: 입력으로 받은 턴 데이터에 `tokenUsage`가 있으면 아래 "토큰
    사용량" 절의 규칙대로 리포트에 포함한다. `read-events.js turn`/`last-turns`가 이
    필드를 반환하지 않는 상황(예: 오래된 스크립트 버전)에서는 이 단계 자체를 생략하고
    억지로 만들어내지 않는다.

## Skill/MCP Tool 활성화 등급

```text
확인됨 (confirmed)
- 명시적인 Skill 또는 MCP Tool 호출이 기록됨
  (예: PreToolUse의 tool_name이 해당 MCP tool과 일치, 또는 프롬프트/답변 텍스트에
  "/plugin-name:skill-name" 같은 명시적 호출 문자열이 관찰됨)

강한 추정 (strongly-inferred)
- 해당 SKILL.md 접근(예: PreToolUse Read, path가 skills/<name>/SKILL.md와 일치)이
  확인되고, 이후 행동이 그 SKILL.md에 정의된 절차와 일치함

약한 추정 (weakly-inferred)
- 행동은 절차와 유사하지만 Skill 파일 접근이나 명시적 호출이 관찰되지 않음
  (우연히 비슷한 순서로 행동했을 가능성을 배제할 수 없음)

관찰 안 됨 (not-observed)
- 관련 이벤트가 전혀 관찰되지 않음
```

**중요**: mason-report가 수집하는 Hook 이벤트에는 "Skill이 호출됐다"를 직접 알려주는 전용
이벤트가 없다. 따라서 기본값은 `약한 추정` 이하이며, `확인됨`으로 판정하려면 위
정의에 맞는 명시적 증거가 실제로 있어야 한다. 증거가 애매하면 등급을 낮춰 잡는다
(과대 확신 금지).

## 등급 → 참고용 수치 변환

mason-report는 Claude의 내부 판단 확률에 접근하지 않는다 — Hook에는 그런 값 자체가
존재하지 않는다. 따라서 아래 %는 실측 확률이 아니라, 위 4단계 등급을 읽기 쉽게 시각화한
**참고용 수치**일 뿐이다("근사"라는 표현은 오히려 "실제 값에 가까운 계산 결과"처럼
오해되기 쉬워 쓰지 않는다). 리포트에 %를 표시할 때는 반드시 이 사실을 함께 명시한다.

```text
확인됨      → 90–100% (참고용)
강한 추정   → 60–89%  (참고용)
약한 추정   → 20–59%  (참고용)
관찰 안 됨  → 알수없음 (수치로 표기하지 않음)
```

**관찰 안 됨은 "0%"라는 숫자를 쓰지 않고 "알수없음"으로만 표기한다.** "0%"는 마치
"관여하지 않았음을 측정해서 확인했다"는 뜻으로 오해되기 쉽지만, 실제로는 판단할 근거
자체가 로그에 없다는 뜻이라 숫자보다 "알수없음"이 더 정확하다.

구간 안에서의 구체적인 숫자(예: "72%")는 등급 내에서의 상대적 위치를 나타내는 표현적
장치이지, 계산된 값이 아니다. 등급 자체보다 숫자를 더 신뢰하지 않도록 리포트 본문에는 항상
등급 이름과 % 참고용 수치를 함께 적는다(% 단독 표기 금지, 관찰 안 됨은 %를 아예 쓰지
않고 "알수없음"만 적는다).

## 프롬프트 문구 → 트리거 매핑

사용자가 리포트에서 가장 궁금해하는 것은 "내 프롬프트의 어떤 문구가 어떤 Skill/Rule/Tool을
유발했는가"다. 이 매핑은 다음 관찰 가능한 신호만으로 구성한다(추측으로 채우지 않는다):

- **명시적 호출**: 프롬프트 원문에 `/plugin:skill` 형태의 문자열이 그대로 있으면, 그
  문자열 자체가 근거 문구다 (`확인됨`).
- **키워드 일치**: 프롬프트에 등장하는 단어/구가 후보 Skill의 `description`에 있는 트리거
  키워드(예: "차트", "배포", "리뷰")와 겹치고, 실제로 그 Skill의 파일 접근 또는 유사 절차
  수행이 관찰되면, 그 단어/구를 근거 문구로 표시한다 (`강한 추정` 이하로 판정 —
  키워드 일치만으로는 `확인됨`을 주지 않는다).
- **지침/Rule 매핑**: `InstructionsLoaded`로 로드된 파일이 프롬프트의 특정 문구와 주제상
  관련되어 보이고, 이후 행동이 그 지침과 일치하면 해당 문구를 근거로 든다. 로드 시점이
  `session_start`인 지침(즉 이 턴의 프롬프트와 무관하게 항상 로드됨)은 특정 문구와 절대
  연결하지 않는다 — "세션 시작 시 무조건 로드됨"으로만 표시한다.
- 위 세 가지 중 어느 것도 해당하지 않으면 해당 트리거는 매핑 표에서 근거 문구를 "없음
  (unknown)"으로 남긴다.

### 트리거 표기 형식

트리거 칸에는 이름만 적지 않고, 그 트리거가 Skill/지침(Rule)/Tool 중 무엇인지를 이름
앞에 괄호로 붙여 한 칸 안에서 바로 구분되게 한다 — 별도의 "종류" 열을 두지 않는다.

```text
(Skill: <skill 이름>)     예) (Skill: dataviz)
(Rule: <파일 경로/이름>)   예) (Rule: CLAUDE.md)
(Tool: <tool_name>)       예) (Tool: Bash), (Tool: mcp__slack__send_message)
```

### 표 가독성 규칙

트리거 매핑 표는 리포트에서 가장 먼저 눈에 들어오는 핵심 결과이므로, 표가 옆으로 길게
늘어져 읽기 어려워지지 않도록 다음을 지킨다.

- **열 개수를 최소화한다**: `근거 문구 | 트리거 | 등급 (참고용 수치)` 3열만 쓴다(트리거
  칸에 종류가 이미 포함되므로 별도 "종류" 열을 추가하지 않는다).
- **근거 문구는 짧게 인용한다**: 프롬프트 원문이 길면 핵심만 약 30자 내외로 잘라 끝에
  "…"를 붙인다. 원문 전체가 필요한 경우에도 표 안에 욱여넣지 않고, 표 위 인용 블록
  (`> "..."`)에서 이미 보여준 내용을 표에서는 다시 반복하지 않는다.
- **한 셀에는 항상 한 줄만 담는다**: 마크다운 표는 셀 내부에 raw newline이 들어가면 표
  구조 자체가 깨지고, `<br>` 같은 HTML 태그는 렌더러에 따라 줄바꿈으로 표시되지 않고
  글자 그대로("&lt;br&gt;") 노출될 수 있어 오히려 가독성을 해친다. 그래서 셀 안에서
  줄을 바꾸는 방식 자체를 쓰지 않는다 — 한 근거 문구가 여러 트리거에 걸치면 한 셀에
  몰아넣지 말고 **행(row)을 트리거 개수만큼 나눠 각 행에 트리거 하나씩만** 적는다
  (근거 문구가 같으면 그대로 반복해서 적는다).
- 표 자체를 여러 줄의 설명 문단으로 대체하지 않는다 — 표가 아닌 문단은 가독성 목적에
  어긋난다.

리포트에서는 이 매핑을 문단이 아니라 표(table)로 제시해 가독성을 확보한다 — 커맨드별
출력 형식(`/mason-report:latest`, `/mason-report:select`, `/mason-report:all`)이 표 컬럼을 정의한다.

## 토큰 사용량

`read-events.js`의 `turn`/`last-turns`는 각 턴에 `tokenUsage` 필드를 함께 반환한다.
이 값은 Skill 활성화 등급과 달리 **실측치**다(Claude 내부 판단을 추정한 게 아니라, Claude
Code 세션 transcript에 실제로 찍힌 API `usage` 값을 그대로 합산한 것) — 그래서 "참고용
%"로 표현하지 않고 숫자를 그대로 적는다. 자세한 계산 방식은
`docs/event-schema.md`의 "토큰 사용량 계산" 절을 따른다.

- `tokenUsage.available`이 `true`이면: `main`(메인 대화)과 `subagent`(Task tool로 실행된
  Subagent, 있는 경우만) 버킷을 **항상 구분해서** 적는다 — 합쳐서 하나의 숫자로 뭉개지
  않는다. 각 버킷 안에서도 `inputTokens`/`outputTokens`(새로 처리·생성된 토큰)와
  `cacheCreationInputTokens`/`cacheReadInputTokens`(캐시 관련 토큰, 과금 체계가 다름)를
  구분해서 표기한다. 이 항목은 `(observed, 로그로 확인된 것)`으로 표시한다.
- `tokenUsage.available`이 `false`이면: `reason`에 따라 다음과 같이 서술하고, 절대 숫자를
  지어내지 않는다 — 모두 `(unknown, 로그만으로 확인 불가)`로 남긴다.
  - `transcript_path_not_captured`: "이 로그는 토큰 사용량 계산 기능이 추가되기 전에
    기록되어 확인 불가"
  - `turn_not_completed`: "이 턴이 아직 완료되지 않아(Stop 미관찰) 계산하지 않음"
  - `transcript_unreadable`: "transcript 파일을 읽을 수 없어 확인 불가"
- Subagent가 하나도 없었던 턴은 `subagent` 버킷의 모든 값이 0이다 — 이 경우 "Subagent
  없음"이라고만 짧게 적고 0을 나열해 표를 늘리지 않는다.
