# decision-analysis

이 Skill은 `.mason-report/events/`에 기록된 JSONL 로그(observed evidence)만을 근거로, Claude
Code가 하나의 사용자 요청을 어떻게 처리했는지를 재구성하는 절차를 정의한다.

## 핵심 원칙

- **이 Skill은 Claude의 비공개 chain-of-thought를 조회하지 않는다.** 로그에 없는 내용은
  아무리 그럴듯해도 "확인됨"으로 서술하지 않는다.
- 모든 판단은 내부적으로 다음 세 등급 중 하나로 분류한다.
  - `observed`: Hook 이벤트 또는 transcript에서 직접 확인된 사실
  - `inferred`: 관찰된 행동을 근거로 재구성한 설명
  - `unknown`: 현재 로그만으로 확인할 수 없는 내용
- "Claude가 이렇게 판단했다"라고 단정하지 말고, "관찰된 행동을 보면 이렇게 판단한 것으로
  추정된다"처럼 서술한다.
- transcript 파일은 비동기로 기록되어 현재 턴의 최신 메시지가 아직 반영되지 않았을 수
  있다. `Stop`/`SubagentStop` 이벤트의 `last_assistant_message`가 있으면 그것을 우선
  신뢰하고, transcript 재조회로 같은 `Stop` 처리를 반복 트리거하지 않는다.
- **리포트 본문은 항상 존댓말(-습니다/-입니다)로 작성한다.** 이 규칙은 사용자에게 실제로
  보여지는 리포트 출력에만 적용된다 — 이 SKILL.md 문서 자체의 설명문은 해당하지 않는다.
- **리포트는 항상 아래 "리포트 구성" 절의 순서**(요약 → 표기 안내 → 1. 요청 → 2. 실제로
  한 일 → 3. 요청 문구별 해석 → 4. 최종 답변 검증 → 원본 로그 → 한계 한 줄)**를 따른다.**
  커맨드가 임의로 순서를 바꾸거나 생략하지 않는다.

## 가독성 원칙

리포트는 "처음 보는 사람이 위에서부터 30초 안에 무슨 일이 있었는지 파악할 수 있는가"를
기준으로 쓴다.

- **결론을 맨 위에 둔다.** 첫 줄의 한 줄 요약만 읽어도 결과를 알 수 있어야 한다.
- **같은 내용은 한 번만 쓴다.** 같은 Tool 호출을 로그 표, 결과 목록, 트리거 표, 풀이
  문장에서 반복하지 않는다. 각 사실은 자기 자리가 정해져 있다(아래 "리포트 구성").
- **근거 등급은 아이콘으로 표시한다.** 문장마다 `(observed, 로그로 확인된 것)` 같은
  긴 태그를 붙이지 않는다. 표기 안내는 리포트 상단에 한 번만 둔다.
- **% 수치를 쓰지 않는다.** Claude의 내부 판단 확률은 Hook에 존재하지 않으므로, %는
  실측값처럼 오해될 뿐 정보를 더하지 않는다. 판정은 아이콘과 짧은 말로만 표시한다.
- **표 셀 안에서는 줄을 바꾸지 않는다.** raw newline은 표를 깨뜨리고, `<br>`은 렌더러에
  따라 글자 그대로 노출된다. 한 셀에 두 가지를 담아야 하면 행을 나눈다.
- **표 셀은 짧게 쓴다.** 프롬프트 문구는 약 30자 내외로 잘라 끝에 "…"를 붙이고, 명령어는
  핵심만 남긴다(예: `git push origin main` — 긴 `cd … &&` 접두어는 뺀다).

## 근거 표기 (아이콘)

리포트 상단에 아래 안내를 **한 번만** 적고, 본문에서는 아이콘만 쓴다.

```text
**표기:** ✅ 로그로 확인됨 · 🔶 정황상 추정 · ❔ 확인할 수 없음
```

| 아이콘 | 내부 등급 | 쓰는 곳 |
|---|---|---|
| ✅ | `observed` / 확인됨 | 로그에 그대로 찍힌 사실, 명시적 호출 |
| 🔶 | `inferred` / 강한 추정·약한 추정 | 관찰된 행동으로 미루어 짐작한 해석 |
| ❔ | `unknown` / 관찰 안 됨 | 로그에 근거가 없어 판단할 수 없음 |
| ❌ | (결과 표시용) | Tool 호출이 실패로 기록됨(`PostToolUseFailure`) — 사실이므로 등급은 `observed` |
| ⚠️ | (검증 표시용) | 최종 답변이 로그와 어긋나거나, 사용자가 알아야 할 주의점 |

- 강한 추정과 약한 추정을 구분해야 하면 판정 칸에 "🔶 추정" / "🔶 약한 추정"으로 적는다.
- ❌와 ⚠️는 필요할 때만 쓰므로 상단 안내에는 넣지 않는다(뜻이 자명하다).
- 사용자가 다른 언어로 대화 중이면 안내 문구를 그 언어로 옮긴다(아이콘은 그대로 쓴다).

## 리포트 구성

아래 순서는 고정이다. 각 항목의 템플릿은 커맨드별 출력 형식(`/mason-report:latest`,
`/mason-report:select`)에 있다.

### 요약 (맨 위)

제목 바로 아래 인용 블록으로 **한두 문장**을 쓴다: 무엇을 요청했고, 실제로 무엇이
됐고, 요청과 어긋난 점이 있으면 무엇인지. 새로운 사실을 여기서 처음 꺼내지 않는다 —
아래 섹션 내용을 압축한 것이어야 한다.

### 표기 안내

"근거 표기 (아이콘)" 절의 한 줄 안내를 그대로 둔다.

### 1. 요청

분석 대상 턴의 사용자 프롬프트(마스킹·길이 제한이 이미 적용된 값)를 인용 블록
(`> "..."`)으로 보여준다.

### 2. 실제로 한 일

Tool 호출을 **목적이 같은 연속 구간끼리 묶은 단계 표**로 보여준다.

표 컬럼: `단계 | 한 일 | 결과`

- **단계**: `① 조사`, `② 수정`, `③ 검증`, `④ 커밋`처럼 번호와 짧은 이름(2~4자)을 쓴다.
  단계 이름은 로그에 찍힌 명령·경로에서 드러나는 목적으로만 붙인다(예: `Edit` 연속 →
  "수정", `npm test` → "검증", `git push` → "푸시"). 목적이 드러나지 않으면 "기타"로 둔다.
- **한 일**: 그 구간에서 다룬 대상(파일, 명령)과 Tool별 호출 횟수를 한 줄로 적는다
  (예: "`package.json` 등 4개 파일 수정 (Edit 5회)").
- **결과**: 그 구간의 Tool 결과를 `PostToolUse`/`PostToolUseFailure`의 `status`/`result`
  에서 그대로 옮긴다. 모두 성공이면 "✅ 성공" 또는 "✅ <핵심 결과>"(예: "✅ 테스트 66개
  통과"), 하나라도 실패하면 "❌ <실패한 Tool>: <에러 요약>"을 적는다. `PostToolUse`가 없는
  호출은 "❔ 결과 기록 없음"으로 적는다.
- `SubagentStart`/`SubagentStop`은 별도 단계로 한 행을 만든다(예: "⑤ 위임 | Explore
  Subagent로 코드 탐색 | ✅ 종료 기록 있음").
- 단계는 시간순이다. 같은 목적이라도 중간에 다른 목적의 호출이 끼어 있으면 별도 단계로
  나눈다.

표 바로 아래에 **지표 한 줄**을 둔다:

```text
소요 시간: <분 초> (<프롬프트 시각> ~ <Stop 시각>) · 도구 호출 <N>회, 실패 <M>회 · 토큰: <아래 "토큰 사용량">
```

Tool 호출이 하나도 없으면 표 대신 "도구를 호출하지 않고 바로 답변했습니다."라고 적고
지표 한 줄은 그대로 둔다.

### 3. 요청 문구별 해석

"프롬프트의 어느 문구가 어떤 행동으로 이어졌는가"를 **표 하나로만** 보여준다. 표 아래에
행마다 풀이 문장을 다시 쓰지 않는다.

표 컬럼: `요청 문구 | 실제 동작 | 판정`

- **요청 문구**: 프롬프트에서 행동과 연결되는 부분(약 30자 내외). 대응하는 문구가 없는
  행동은 "(문구 없음)"으로 적는다.
- **실제 동작**: 그 문구에 대응하는 관찰된 행동을 짧게 적는다(예: "`git push`",
  "dataviz Skill 파일을 읽고 차트 작성"). 요청했는데 대응 행동이 없으면 "<무엇> 없음"으로
  적는다(예: "머지 명령 없음 (브랜치 확인만 함)").
- **판정**: 아이콘 + 짧은 말. 예: "✅ 실행됨", "🔶 추정", "🔶 약한 추정", "❔ 실행 안 됨".
  사실과 해석이 섞이면 "✅ 실행됨 / 🔶 minor 올림으로 해석"처럼 `/`로 나눠 한 셀에 적는다.
- 판정 기준은 아래 "Skill/MCP Tool 활성화 등급"과 "프롬프트 문구 → 트리거 매핑" 절을
  따른다.

표 아래에 **Skill·지침 한 줄**을 둔다:

- 관찰된 게 있으면: "사용된 Skill: <이름> (<근거>) · 로드된 지침: <파일> (<loadReason>)"
- 없으면: "사용된 Skill·지침은 로그에 없습니다."
- `session_start`로 로드된 지침은 특정 문구와 연결하지 않고 이 줄에만 "(세션 시작 시
  항상 로드)"로 적는다.

### 4. 최종 답변 검증

`Stop.data.lastAssistantMessage`를 "2. 실제로 한 일"과 비교한 결과를 **불릿 2~4개**로
적는다. 각 불릿은 아이콘으로 시작한다.

- ✅: 답변 내용이 로그와 일치함(무엇이 일치하는지 구체적으로)
- 🔶: 답변의 설명이 로그와 모순되지 않지만 직접 확인되지는 않음
- ⚠️: 답변이 로그와 어긋나거나, 요청과 다르게 처리된 점
- ❔: 답변 내용 중 로그로 확인할 수 없는 부분

`Stop`이 없으면(턴 미완료) "❔ 최종 답변이 아직 기록되지 않았습니다."만 적는다.

### 원본 로그 (접힌 상태)

실제 이벤트 전체를 `<details>` 블록 안에 둔다 — 궁금한 사람만 펼쳐 볼 수 있게 한다.
(`<details>`를 지원하지 않는 렌더러에서는 펼쳐진 채로 보이지만 내용은 그대로 읽힌다.)

```markdown
<details>
<summary>원본 로그 <행 수>건 펼치기</summary>

| 시각 | 이벤트 | 내용 |
|---|---|---|
| ... | ... | ... |

</details>
```

- **시각**: `HH:MM:SS`.
- **이벤트**: 이벤트명 대신 아래 쉬운 말을 쓴다. 같은 `toolUseId`의 `PreToolUse`와
  `PostToolUse`/`PostToolUseFailure`는 한 행으로 합친다(시각은 `PreToolUse` 기준). 짝이
  없는 `PreToolUse`는 "도구 시작 → 기록 없음"으로 적는다.

  ```text
  UserPromptSubmit                → 프롬프트 입력
  InstructionsLoaded              → 지침 로드
  PreToolUse + PostToolUse        → 도구 시작 → 성공
  PreToolUse + PostToolUseFailure → 도구 시작 → 실패
  SubagentStart                   → Subagent 시작
  SubagentStop                    → Subagent 종료
  Stop                            → 턴 종료
  ```
- **내용**: Tool명 + 핵심 입력(경로/명령/패턴), 지침은 `path` + `loadReason`, 프롬프트와
  최종 답변은 짧게 축약한다. 결과 요약은 넣지 않는다(이미 "2. 실제로 한 일"에 있다).
- `promptId` 없이 시간 구간으로만 연결된 이벤트(`timeWindowCorrelated`)는 내용 앞에
  "🔶 "를 붙이고, 표 아래에 "🔶 표시된 행은 시간 구간으로만 이 턴에 연결한 이벤트입니다."
  라고 한 줄 적는다. 모두 `promptId`로 연결됐으면 이 줄을 생략한다.
- 이벤트를 생략하지 않는다. 행 수가 많아도 모두 적는다(접혀 있으므로 본문 가독성을
  해치지 않는다).
- 이벤트가 하나도 없으면 `<details>` 블록 대신 "이 턴에서 관찰된 이벤트가 없습니다."라고
  적는다.

### 한계 (한 줄)

맨 끝에 다음 한 줄을 둔다(다른 언어면 그 언어로 옮긴다):

```text
> ℹ️ 이 리포트는 로그를 바탕으로 재구성한 것이며, Claude의 내부 사고 과정이 아닙니다.
```

리포트 안에서 특별히 밝혀야 할 한계(예: 로그 회전으로 일부 유실, 요청한 턴 수보다 로그가
적음)가 있으면 이 줄 뒤에 짧게 덧붙인다.

## 분석 절차

1. **분석 대상 식별**: 분석할 `sessionId`와 (있다면) `promptId`를 확정한다.
2. **최초 프롬프트 확인**: 해당 턴의 `UserPromptSubmit.data.prompt`를 확인한다. 이 값은
   저장 시 마스킹·길이 제한이 적용된 값이므로, 원문 그대로가 아닐 수 있다는 점을 인지한다.
3. **로드된 지침 확인**: 같은 턴(또는 세션 시작 시점)의 `InstructionsLoaded` 이벤트를
   모아 어떤 파일이 로드됐는지 확인한다. 파일이 "로드됨"과 그 내용이 "실제로 적용됨"은
   별개다 — 이 구분은 8단계에서 다시 판단한다.
4. **시간순 정렬과 짝 맞추기**: 이벤트를 `timestamp` 기준으로 정렬하고, 같은
   `toolUseId`의 Pre/Post를 짝지운다. `promptId`로 연결된 이벤트는 observed 근거로,
   시간 구간으로만 연결된 이벤트는 inferred(약한 연결)로 표시한다.
5. **단계 묶기**: 짝지운 Tool 호출을 목적이 같은 연속 구간끼리 묶어 "2. 실제로 한 일"
   표를 만든다. 결과는 로그에 찍힌 `status`/`result`만 옮긴다(새로 판단하지 않는다).
6. **지표 계산**: 소요 시간(프롬프트 → `Stop`), 도구 호출 수(짝 기준), 실패 수
   (`PostToolUseFailure` 수), 토큰 사용량을 계산한다.
7. **Skill 적용 여부 판단**: 아래 "Skill/MCP Tool 활성화 등급"으로 각 후보를 판정하고,
   근거가 된 프롬프트 문구를 찾는다. 근거 문구를 특정할 수 없으면 "(문구 없음)"으로
   남긴다 — 등급을 맞추기 위해 문구를 억지로 짜내지 않는다.
8. **Rule/지침 적용 여부 판단**: 3단계의 지침 각각에 대해, 이후 행동이 그 지침 내용과
   일치하는지 같은 등급 체계로 판단한다. 로드됐다는 사실만으로 "적용됨"이라 단정하지 않는다.
9. **요청 문구별 해석 표 작성**: 프롬프트를 행동 단위의 문구로 나누고, 문구마다 대응하는
   관찰 행동과 판정을 적는다. 요청했지만 대응 행동이 없는 문구도 반드시 행으로 남긴다.
10. **최종 답변 검증**: `Stop.data.lastAssistantMessage`와 5~6단계 결과를 비교해 일치,
    불일치, 과도한 단정, 누락을 찾는다.
11. **요약 작성**: 1~10단계 결과를 한두 문장으로 압축해 리포트 맨 위에 둔다.
12. **확인 불가 항목 표기**: 로그가 없거나, 파일이 회전되어 유실됐거나, 스키마가 예상과
    달라 판단할 수 없는 항목은 ❔로 남긴다. 빈 자리를 그럴듯한 서술로 채우지 않는다.

## Skill/MCP Tool 활성화 등급

```text
확인됨 (confirmed) → ✅
- 명시적인 Skill 또는 MCP Tool 호출이 기록됨
  (예: PreToolUse의 tool_name이 해당 MCP tool과 일치, 또는 프롬프트/답변 텍스트에
  "/plugin-name:skill-name" 같은 명시적 호출 문자열이 관찰됨)

강한 추정 (strongly-inferred) → 🔶 추정
- 해당 SKILL.md 접근(예: PreToolUse Read, path가 skills/<name>/SKILL.md와 일치)이
  확인되고, 이후 행동이 그 SKILL.md에 정의된 절차와 일치함

약한 추정 (weakly-inferred) → 🔶 약한 추정
- 행동은 절차와 유사하지만 Skill 파일 접근이나 명시적 호출이 관찰되지 않음
  (우연히 비슷한 순서로 행동했을 가능성을 배제할 수 없음)

관찰 안 됨 (not-observed) → ❔
- 관련 이벤트가 전혀 관찰되지 않음
```

**중요**: mason-report가 수집하는 Hook 이벤트에는 "Skill이 호출됐다"를 직접 알려주는 전용
이벤트가 없다. 따라서 기본값은 `약한 추정` 이하이며, `확인됨`으로 판정하려면 위 정의에
맞는 명시적 증거가 실제로 있어야 한다. 증거가 애매하면 등급을 낮춰 잡는다(과대 확신 금지).

"관찰 안 됨"은 "관여하지 않았음을 확인했다"가 아니라 "판단할 근거가 로그에 없다"는
뜻이다. 그래서 ❔로 표시하고, "0%"나 "관여 안 함" 같은 표현을 쓰지 않는다.

## 프롬프트 문구 → 트리거 매핑

"3. 요청 문구별 해석" 표의 판정은 다음 관찰 가능한 신호만으로 구성한다(추측으로 채우지
않는다):

- **명시적 호출**: 프롬프트 원문에 `/plugin:skill` 형태의 문자열이 그대로 있으면, 그
  문자열 자체가 근거 문구다 (✅).
- **직접 대응하는 Tool 호출**: 문구가 요구한 행동이 그대로 Tool 호출로 찍혔으면
  (예: "푸시" → `git push`) ✅로 판정한다. 실행 방식에 해석이 섞였으면(예: "버전 하나
  올려" → minor를 올림) 사실(✅)과 해석(🔶)을 `/`로 나눠 적는다.
- **키워드 일치**: 프롬프트 단어가 후보 Skill의 `description` 트리거 키워드와 겹치고,
  실제로 그 Skill의 파일 접근 또는 유사 절차 수행이 관찰되면 🔶로 판정한다 — 키워드
  일치만으로는 ✅를 주지 않는다.
- **지침/Rule 매핑**: `InstructionsLoaded`로 로드된 파일이 문구와 주제상 관련되고, 이후
  행동이 그 지침과 일치하면 🔶로 판정한다. `session_start`로 로드된 지침은 특정 문구와
  연결하지 않는다.
- 위 어느 것도 해당하지 않으면 ❔로 남긴다.

## 토큰 사용량

`read-events.js`의 `turn`/`last-turns`는 각 턴에 `tokenUsage` 필드를 함께 반환한다. 이
값은 Claude Code 세션 transcript에 실제로 찍힌 API `usage` 값을 합산한 **실측치**다(✅).
자세한 계산 방식은 `docs/event-schema.md`의 "토큰 사용량 계산" 절을 따른다. 값은 "2. 실제로
한 일" 아래 지표 한 줄의 "토큰:" 자리에 넣는다.

- `tokenUsage.available`이 `true`이면:
  `토큰: 입력 <inputTokens> · 출력 <outputTokens> · 캐시 생성 <cacheCreationInputTokens> · 캐시 조회 <cacheReadInputTokens>`
  Subagent 버킷에 0이 아닌 값이 있으면 뒤에 ` (Subagent: 입력 … · 출력 … · 캐시 생성 … · 캐시 조회 …)`를
  붙여 메인과 구분한다. 모두 0이면 Subagent 부분은 생략한다. 숫자는 천 단위 쉼표로 적는다.
- `tokenUsage.available`이 `false`이면 숫자를 지어내지 않고 `reason`별로 짧게 적는다:
  - `transcript_path_not_captured`: "❔ 옛 로그라 기록이 없습니다"
  - `turn_not_completed`: "❔ 턴이 끝나지 않아 계산하지 않았습니다"
  - `transcript_unreadable`: "❔ transcript를 읽을 수 없습니다"
- 입력 데이터에 `tokenUsage` 필드 자체가 없으면(오래된 스크립트) "토큰:" 항목을 생략한다.
